> 执行时间：2026-11-20
> 环境：Windows / x86_64-pc-windows-msvc / Rust 1.98.0 / 屏幕 2560×1440 / 系统缩放 100%
> 证据文件：`desktop/probe-results/capture/*.png`

## 1. 工程与产物体积

- Rust 1.98.0，edition 2024，`windows` 0.62.2
- release profile：`opt-level="z"` + `lto="fat"` + `codegen-units=1` + `panic="abort"` + `strip`

| 产物 | 体积 |
|---|---|
| `pombotd.exe`（托盘 + 热键） | **271 KB** |
| `probe_capture.exe`（含 PNG 编码） | 286.5 KB |
| `probe_ocr.exe`（含 WinRT OCR） | 294.5 KB |
| `probe_input.exe` | 136 KB |

**判断：体积指标远超预期。** 原计划担心"空壳 2~5 MB、带托盘 5~8 MB"，实测连 300 KB 都不到，因为 WinRT OCR 走系统组件、不静态链接。

这反过来说明一件事：**选 Rust 换来的体积收益比想象中大得多**，而 271 KB 也意味着后续可以毫无压力地加功能，不必为了几十 KB 纠结。

**冷启动**：从 `main` 入口到托盘图标创建完成 **45 ms**（进程外部创建开销另计，通常再加 30~50 ms）。用户双击到看见托盘在 100 ms 内。

## 2. 托盘与全局热键（T0.3）

`tray-icon` 0.26 + `global-hotkey` 0.10 在 Windows 上可用，但有两个必须遵守的条件：

1. **托盘与热键必须和消息泵同线程**。不能在子线程创建后主线程空转。
2. **没有内建事件循环**，必须自己泵消息：`PeekMessageW` + `try_recv` 轮询事件通道。`GetMessageW` 阻塞式循环不可用，因为那样无法轮询热键事件。

当前实现以 16 ms 周期轮询，进程稳定存活，`Alt+Space` 可触发。

> 后续接入 WS 服务时，这个循环会改为 tokio 运行时 + 独立的窗口消息线程，或改用 `WndProc` 回调驱动。

## 3. 截图（T0.4）—— 本次最重要的结论

### 结果矩阵

| 目标 | 类型 | `BitBlt`(窗口DC) | `PrintWindow` | `PrintWindow`+`RENDERFULLCONTENT` |
|---|---|---|---|---|
| 整个桌面 | — | **可用**（亮度 35.8） | — | — |
| Firefox | 浏览器 | 可用（35.7） | 可用（39.0） | 可用（92.7） |
| CodeBuddy CN | **Electron / Chromium** | **黑屏 99.1%** | **黑屏 100%** | **可用（36.1）** |
| 设置 | **WinUI / UWP** | **黑屏 100%** | **黑屏 100%** | **可用（38.6）** |

耗时（2560×1440）：`PrintWindow` 14~16 ms，`PrintWindow_FULL` 29~38 ms。

### 判断

**`PW_RENDERFULLCONTENT` 是唯一能截到 GPU 合成窗口的方式，必须作为主路径。**

- `BitBlt(窗口DC)` 和裸 `PrintWindow` 在 Chromium 系与 WinUI 上完全失效——这不是参数没调对，是渲染路径决定的（内容在合成器里，不在窗口的绘制上下文里）。
- Firefox 三种都可用，说明它部分场景仍走传统绘制路径，不能拿它当"浏览器能不能截"的判断依据。
- 截图耗时 30 ms 量级，每步一次完全可接受。

### 附带发现一（重要，会影响 M4）：`GetWindowRect` 有 8px 系统性偏移

用 `DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)` 做对照，实测结果：

| 窗口 | `GetWindowRect` | DWM 可见边界 | 差值 |
|---|---|---|---|
| CodeBuddy（Electron） | (-8,-8) 2576×1456 | (0,0) 2560×1440 | **四边各 8 px** |
| 设置（WinUI） | (0,8) 2560×1440 | (0,8) 2560×1440 | 0 |

**结论：偏差不是普遍的，但对 Chromium/Electron 这类带 DWM 缩放的窗口是每边 8 px。** 直接拿 `GetWindowRect` 的原点算坐标，点击会整体偏移 8 px，小控件必然点错。

**对策：窗口几何一律取 `DWMWA_EXTENDED_FRAME_BOUNDS`**，`GetWindowRect` 只保留用于对比诊断。已实现于 `gui::capture::{outer_bounds, visible_bounds}`。

### 附带发现二：DPI 感知必须靠清单声明，不能只靠运行时调用

`SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)` 在 `main` 一开始就调用了，但这种方式**依赖调用顺序**：任何在其之前发生的 DPI 相关调用，或清单里已有的声明，都会让它失效（返回 FALSE 且不报错）。

rustc 默认嵌入的清单里带有 DPI 声明，因此正确做法是自己嵌一份：

```xml
<dpiAware xmlns="http://schemas.microsoft.com/SMI/2005/WindowsSettings">true/pm</dpiAware>
<dpiAwareness xmlns="http://schemas.microsoft.com/SMI/2016/WindowsSettings">PerMonitorV2, PerMonitor</dpiAwareness>
```

实现方式：`assets/pombot.rc` 里 `1 24 "assets/pombot.manifest"`，`build.rs` 用 `embed_resource` 编进所有产物。

**验证结果**：进程与线程均报告 `PER_MONITOR_AWARE`。这条对多显示器与运行时切换缩放是必需的，SYSTEM_AWARE 在多屏不同 DPI 下会直接算错。

> 顺带记一个坑：`DPI_AWARENESS` 的取值是 `INVALID=-1 / UNAWARE=0 / SYSTEM_AWARE=1 / PER_MONITOR_AWARE=2`，**不是从 1 开始**。按"1、2、3"去映射会把 PER_MONITOR_AWARE 误判成 SYSTEM_AWARE，白排查半天。用 `GetProcessDpiAwareness` 交叉验证可以避免。

## 4. 坐标注入（T0.5）

100% 缩放下的结果：

| # | 目标 (px) | 实际 (px) | 误差 |
|---|---|---|---|
| 0 | 128,72 | 128,72 | 0 |
| 1 | 2431,72 | 2431,72 | 0 |
| 2 | 1280,720 | 1280,720 | 0 |
| 3 | 128,1367 | 128,1367 | 0 |
| 4 | 2431,1367 | 2431,1367 | 0 |

**5/5 通过，最大误差 0 px。**

换算公式（已验证）：

```rust
// 物理像素 -> SendInput 归一化
nx = (x - virtual_x) * 65535 / (virtual_w - 1)
ny = (y - virtual_y) * 65535 / (virtual_h - 1)
// 注入标志：MOUSEEVENTF_MOVE | MOUSEEVENTF_ABSOLUTE | MOUSEEVENTF_VIRTUALDESK
```

两个容易写错的点，已固化在代码里：

1. **分母必须是 `size - 1`**，用 `size` 会让最右/最下各少 1 px 命中区。
2. **必须先调用 `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)`**，否则 `GetSystemMetrics` 返回虚拟化值，坐标整体偏移。

### 待补

- **150% 缩放未测**（当前环境是 100%）。这是国内最常见设置，必须补。
- **多显示器未测**（当前只有单屏，虚拟桌面原点为 0,0）。副屏在主屏左侧时原点为负数，是符号错误高发区。

### 已用单测锁定的部分

坐标换算是纯数学，与系统 DPI 无关的部分已抽成 `normalize_point` / `denormalize_point` 并覆盖四个用例：

- 单屏 2560×1440 往返误差 ≤ 1 px
- 四角精确落在 0 与 65535（分母写成 `size` 而非 `size-1` 会在这里失败）
- 负原点 `(-1920, 0, 4480×1440)` 往返且结果不越界（副屏在左侧的典型布局）
- 奇数尺寸与 4K 竖屏 `(1921×1081 / 3840×2160 / 2160×3840 / 800×601)`

`probe_dpi.exe` 负责实机验证：逐屏打印矩形、DPI、缩放，再对每块屏的中心与四角做落点比对。切换缩放或插拔显示器后直接重跑即可。

## 5. OCR（T0.6）

### 语言支持

`available_languages = ["en-US", "zh-Hans-CN"]`，中文引擎可用。

### 耗时（关键）

| 场景 | 原尺寸 | 放大 2 倍 |
|---|---|---|
| 全屏 2560×1440 | **779 ms** | **2101 ms** |
| 局部 700×260 | **59 ms** | **98 ms** |

**判断：绝对不能用全屏识别。** 779 ms 的单步开销会让 30 步任务固定多花 23 秒，而放大 2 倍更是到 2 秒。局部识别 59~98 ms 才是可用区间。

这直接支持了设计里的"局部裁剪"策略，也说明**感知层必须先靠窗口矩形或上一次点击位置推测目标区域**，而不是整屏丢给引擎。

### 准确率与两个中文特有现象

同一画面、同一区域的两组输出：

```
原尺寸:   18:11 @ 提 醒 事 项 5 条 通 知 弹 幕 到 现 26 。
放大2倍:  18:11 提醒事项 5 条 通知 弹幕到现
```

**现象一：中文逐字返回，字与字之间插空格。**
"提醒事项" 变成 "提 醒 事 项"。这会让任何字符串匹配失效——查 `"确定"` 永远匹配不到 `"确 定"`。

**对策**：所有 OCR 结果与匹配目标都必须先做**去空格归一化**（去掉所有空白字符再比）。这一条要在 T4.6 里做成强制步骤，不是可选项。

**现象二：放大 2 倍后字符分组恢复正常。**
2 倍放大后 "提醒事项" 正确连成一个词。这是放大除提升清晰度之外的额外收益，进一步说明**放大应作为默认策略**，而不是遇到问题才开。

### 准确率边界

全屏识别长文本时有明显错误：

| 正确 | 识别结果 |
|---|---|
| `src` | `SrC` |
| `增加多少` | `加 多 少` |
| `.gitignore` | `.gftlgnore` |

**判断**：这套 OCR 适合"判断界面有没有变化"和"读清按钮上的 2~4 个字"，不适合精确读取路径、代码、编号。

**因此 `ort` + PP-OCR 精读通道的触发条件已经明确**：当出现"必须读准"的场景（订单号、金额、错误码、文件路径）时再引入，不要提前投入 2~3 周。

## 6. 对 M4 的直接影响

以下是本次探针改变了或确认了实现细节的地方：

1. **截图只保留一条主路径**：`PrintWindow + PW_RENDERFULLCONTENT`。`BitBlt` 仅用于整屏基准与黑屏对照，不作为窗口截取方案。
2. **窗口矩形一律用 `DWMWA_EXTENDED_FRAME_BOUNDS`**，禁止用 `GetWindowRect` 直接算坐标（会偏 8 px）。
3. **OCR 强制裁区域**，并内建"去空格归一化"与"默认放大 2 倍"两个处理步骤。
4. **坐标公式已确定**，但必须在 150% 缩放与多显示器环境下复测后才能判定"M4 完成"。
5. **黑屏判定不能只看整屏基准**：Electron / WinUI 窗口在错误的方式下会是 100% 黑，用 `mean_luma < 8 && black_ratio > 0.99` 判定可靠有效，可直接复用。

## 8. 一句话总结

四个探针全部通过，其中截图这一项得出了决定性结论：**在这台机器上，除了 `PW_RENDERFULLCONTENT`，没有任何方式能截到 Chromium 系和 WinUI 窗口**。这条结论如果晚三周才发现，M4 的整条截屏链路都要重写。
